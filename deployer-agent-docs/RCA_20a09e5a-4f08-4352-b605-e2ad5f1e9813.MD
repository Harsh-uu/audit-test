# RCA — "Supervision with Rachel Moss" achievements leaking into Daniel Okafor's portfolio

## Scope
Read-only diagnostic against the LIVE PRODUCTION database of deployment `transcript-vault-2`
(active run `20a09e5a-4f08-4352-b605-e2ad5f1e9813`, db `transcript-vault-2-supervision_db`).

## Headline findings

### 1. This app is MongoDB, not Postgres — the migration premise does not apply
- Template: `fastapi_react_mongo_shadcn_base_image`; the production datastore is MongoDB Atlas.
- `list_collections` returns 23 collections; there is **NO `schema_migrations` collection** (and no SQL
  migration ledger of any kind).
- Therefore the request to confirm versions `037_backfill_sign_off_manager_id`,
  `038_backfill_sign_off_manager_id_from_attendees`, `039_fix_sign_off_manager_admin_misattribution`
  **cannot be answered as framed** — there is no migration table in production to read. Any "backfill
  migration" logic in a Mongo app is ordinary application/startup code, not a tracked SQL migration, so
  its presence can't be proven or disproven from a migrations ledger.

### 2. The reported records DO NOT EXIST in the production database
- **Users:** 17 total across 4 orgs. No user named "Daniel Okafor" or "Rachel Moss" (regex on `name`
  for `Okafor|Moss|Daniel|Rachel` → 0). No email `danielo@…`. The `1two.one` org users are:
  Admin Alex, Amanda, Health visitor, Hello test, O T, Super Admin.
- **Meeting:** 40 total. No meeting with title containing "Rachel Moss". The only titles containing
  "Supervision" are "Supervision with Alex" (Eddie Stevens Care Ltd) and "Supervision with Harvey"
  (Test Company). There is **no meeting dated 21 Aug 2026** — the newest meeting in production is
  dated **2026-08-01**.
- **Bug-class scan:** meetings where `sign_off_manager_name` is set but `sign_off_manager_id` is null → **0**.

### 3. Production data is stale relative to the deployed code
- Newest meeting in prod: 2026-08-01. Most recent successful redeploys: 2026-10-17.
- Redeploys do NOT migrate preview data into production (data migration happens on the INITIAL deploy
  only). So the Daniel/Rachel/21-Aug dataset the screenshot shows is not present in the production DB
  that the live app reads.

## Root cause of "can't find / still leaking"
The specific meeting, its `sign_off_manager_id`/`sign_off_manager_name`/`sign_off_record`/`attendees`,
and both users are **absent from the production database**. The symptom in the screenshot was therefore
almost certainly produced against the PREVIEW environment's database (where that test data lives), not
the live production DB. Nothing in production matches the reported scenario, so the leak cannot be
reproduced or attributed to any of the three shipped fixes (or a 4th scenario) from production data —
the data they key off simply isn't there.

## What I could NOT determine (and why)
- The actual `sign_off_manager_id` / `sign_off_record` / `attendees` for that meeting — the document
  does not exist in production.
- Whether the three "fixes" ran — there is no Mongo migration ledger to inspect; confirmation must come
  from the application code/logs, not a schema_migrations table.

## Suggested next steps
1. Confirm which URL the screenshot came from — the production host `https://transcript-vault-2.emergent.host`
   (and custom domains `1two.one` / `www.1two.one`) vs. the preview app. If it was preview, the bug is a
   preview-DB data state, not a production issue.
2. If the scenario must be validated in production, the Daniel/Rachel dataset has to be created or copied
   into production (DB Manager preview→prod copy) first — redeploys alone will never bring it over.
3. The migration-ledger check (037/038/039) is not meaningful for this Mongo app; verify the fix logic
   from the deployed source/startup code instead.
