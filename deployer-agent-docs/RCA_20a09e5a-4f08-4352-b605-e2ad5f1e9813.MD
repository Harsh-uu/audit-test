## Root cause (code-level, verified from source)
The portfolio exclusion lives in `backend/routers/portfolio.py` in TWO functions, both using
the same meeting-selection predicate:

    AND (sign_off_manager_id IS NULL OR sign_off_manager_id != $2::uuid)   -- $2 = viewing user
    AND EXISTS (... jsonb_array_elements(attendees) elem WHERE elem->>'user_id' = $2::text)

A meeting is EXCLUDED from a viewer's own portfolio only when `sign_off_manager_id = <viewer>`.
The `sign_off_manager_id IS NULL` branch means: if that column is NULL, the row is KEPT.
So a meeting leaks into the manager's OWN view when BOTH hold:
  (a) sign_off_manager_id IS NULL (never backfilled) — exclusion is a no-op, AND
  (b) the manager's user_id is present in the meeting's `attendees` JSONB (he is listed as an
      attendee because he conducted it).

Why the leak is specifically in **Achievements** and not the meetings list:
- `_build_portfolio_data` (meetings list, line ~121) restricts to `status IN ('signed_off','shared')`.
- `_build_portfolio_registers` (Achievements/Actions/Learning-Needs, line ~323) deliberately
  does NOT restrict status (docstring: pulls from ANY analysed meeting regardless of status,
  only `analysis_id IS NOT NULL`).

Now the migration coverage gap. All three deployed backfills are STATUS-GATED:
- m037: `UPDATE meetings SET sign_off_manager_id = (sign_off_record->>'signed_by')::uuid
         WHERE status IN ('signed_off','shared') AND sign_off_manager_id IS NULL`
- m038: backfill from attendees manager/admin `WHERE status IN ('signed_off','shared') AND
         sign_off_manager_id IS NULL`
- m039: admin-misattribution correction `WHERE status IN ('signed_off','shared') …`

=> Any meeting in a status OTHER than signed_off/shared (e.g. completed/analysed/review/draft)
still has `sign_off_manager_id = NULL`. The Achievements path (any-status) therefore keeps
those rows via the `IS NULL` branch, and because the conducting manager (Daniel) is in the
attendees array, the EXISTS clause matches him → his own supervisee meetings ("Supervision
with Rachel Moss", "Supervision with Diane Fletcher") leak into HIS personal Achievements.

This is the same bug class as before (sign_off_manager_id unset), now exposed on the
non-signed-off meetings that the earlier status-gated backfills never touched.

## The fix is already written — it just hasn't run in production
m040 = '040_backfill_sign_off_manager_id_any_status'. The name says it drops the
`status IN ('signed_off','shared')` restriction — i.e. it backfills sign_off_manager_id for
meetings of ANY status, which is exactly the gap above. It is NOT in the active run's source,
so it has not executed. Deploying/restarting production runs the migration ledger and applies
m040.

## Remaining risk to verify (could not check against live data)

m038/m039 deliberately left `sign_off_manager_id` NULL when a meeting had 0 or 2+
