# RCA — "No invite/welcome email when creating staff users in production"

**Deployment:** transcript-vault-2 (`efbb8ed3-1617-4188-b020-fd0c81507da3`)
**Active run inspected:** `5e555a8a-0690-4d76-bf06-48e67a636b2f` (success, currently serving)
**Window:** last 24h (Loki max `since_minutes=1440`)

## Verdict
This is **(a) expected behaviour being misunderstood — NOT a Resend regression.** The customer's "create staff user" actions all hit `POST /api/org/invite-user`, which by design sends no email. The Resend-based admin-invite path (`send_invite_email` in `utils/org_provisioning.py`) was **never reached** in the observed window, so there is no swallowed exception and no bad-`RESEND_API_KEY` failure to fix here.

## Evidence

### 1. Which endpoint the customer's "create user" actions hit → `POST /api/org/invite-user`
Access logs from the customer IP `8.233.137.176` show repeated:
```
INFO: 8.233.137.176:0 - "POST /api/org/invite-user HTTP/1.1" 200 OK   (multiple times)
INFO: 8.233.137.176:0 - "GET  /api/org/structure HTTP/1.1" 200 OK
```
Per the source review, `POST /api/org/invite-user` (routers/org.py) creates the user with an admin-set password and contains **no email-sending code** — the "pending invite" UI is a manual "share this login info" flow. So zero email is expected and correct for this action.

### 2. The Resend admin-invite path was never hit (nothing swallowed)
Log filter `Invite email|send_invite|invite_admin|resend|Resend` over 24h → **0 lines**. `send_invite_email()` logs "Invite email sent to" on success and "Invite email failed" on its broad except; neither appeared. A broader sweep (`admin|onboard|provision|stripe|WARNING|Warning|Exception|Traceback`) returned 161 events, all INFO/200 (a few benign 404s on non-existent `/api/admin/*` probe paths) — **no warnings, exceptions, or tracebacks**. Conclusion: the Resend path did not run and did not silently fail. (A Stripe checkout session was created at 2026-10-16 10:46 but produced no corresponding admin-invite email log, i.e. no admin invite was sent/attempted in-window.)

### 3. RESEND_API_KEY secret state
`list_secrets` on the active run: `RESEND_API_KEY` is **present and non-empty** (`is_empty:false`). `SENDER_EMAIL` is also present/non-empty (consistent with the user's statement it's set to the verified `noreply@notify.1two.one`).
- Format caveat: I could **not** verify the `re_...` prefix. The `matches_expected` check only does exact-string equality (returned false against a literal probe, as expected) and never reveals the value. So presence + non-empty is confirmed; the key *format/validity* is unverified by tooling — but this is moot here because the admin-invite path was never invoked.

## What this means
- Staff "Add User" (People & Usage / Structure tab) → `POST /api/org/invite-user` → **no email by design.** Working as intended.
- The only email-sending path (`invite_admin_core()` / `send_invite_email()`) is for inviting a new **org admin** (Super Admin creating an org, or Stripe self-serve paid-signup onboarding) — it was not exercised by the customer's staff-creation actions.

## Recommended actions
1. **User / product decision:** Clarify with the customer that staff "Add User" never emails by design. If they *want* staff to receive a welcome/invite email, that is a **feature request**, not a bug.
2. **Code (only if the desired behaviour is "staff should get an email"):** E1 would need to add an email send to `POST /api/org/invite-user` in routers/org.py (reusing the existing Resend helper). This is a new capability, not a regression fix.
3. **Pre-emptive (admin-invite path):** If/when an org-admin invite *is* triggered, re-pull logs and look for "Invite email failed" to validate `RESEND_API_KEY`. Because that path swallows all exceptions and logs only a warning, a bad/missing key there would be invisible to the frontend — worth tightening later, but not the cause of the current report.

## Caveat on scope
Loki is limited to a 24h window. The evidence above is representative (multiple invite-user calls fall inside it and match the complaint). If the customer insists an admin-invite (not staff add-user) was attempted earlier and got no email, re-trigger with the approximate timestamp/org_id so logs can be pulled closer to that event.
