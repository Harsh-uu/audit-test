## TL;DR
Production is **rate-limited**, not misconfigured. Every `POST /api/auth/login` for the superadmin in the last 24h returned **HTTP 429 Too Many Requests** — the app's own per-account MFA limiter (`login_attempts`, identifier `mfa_send:{user_id}`, max 8 sends / 24h) tripped and rejected the request **before** `_generate_and_send_mfa` ever called Resend. That is why no email goes out. The reset you did only touched **preview's** database; production's rate-limit counter is independent and still exhausted.

## Evidence from production (not inferred)

## Root cause
The MFA send path is being short-circuited by the **production** rate limiter. Because the 429 is returned before the Resend call, the state of `RESEND_API_KEY`/`SENDER_EMAIL` is irrelevant to the *current* symptom — they are set and the send code is never reached.

Your preview reset of the `mfa_send:{superadmin}` row did not help production for one of two reasons (both land on the same fix):
- **(a) Production points at a different database than preview.** `DATABASE_URL`/`APP_DATABASE_URL` are set in production, but deployment secret values are **NOT overwritten on redeploy** — if you changed preview's `.env` `DATABASE_URL` after production was first deployed, production can still be bound to the *original* DB/Supabase project. In that case the row you cleared in preview's DB has zero effect on prod. **I cannot read secret VALUES, so I could not confirm same-vs-different DB from here** — you must verify this (see Fix 2).
- **(b) Same DB, but the counter was re-exhausted in production.** Repeated superadmin login attempts against production (the logs show multiple back-to-back 429s plus a burst of `refresh`/`me` 401s) can burn through the 8-per-24h cap again after any reset.

## What I could NOT verify (tooling limits — stated honestly)
- **Secret VALUE equality (preview `.env` vs production).** Values are never returned by any tool. Presence/non-empty is confirmed above; exact value match is not. If you give me the expected values I can run a sealed `matches_expected` comparison without exposing them — otherwise compare in Deployment Panel → Secrets.
- **The `login_attempts` row itself.** The rate-limit state lives in **Postgres/Supabase**, and my only DB tool (`mongo_query`) reaches the deployment's Mongo, not Postgres. I could not read or clear the production `mfa_send:{superadmin}` row directly. The 429 in the production logs is nonetheless conclusive that the limiter is tripped in prod.

## Fix (root cause)
1. **Clear the rate-limit row in PRODUCTION's database** (not preview's): delete/zero the `login_attempts` row for identifier `mfa_send:{superadmin user_id}` in the **actual Supabase/Postgres project that production is bound to**. This is in Supabase, which I have no access to. After clearing, attempt exactly one superadmin login and watch for the email (don't retry in a loop — each retry re-increments toward the 8/24h cap).
2. **Confirm which DB/secrets production is actually using.** In Deployment Panel → Secrets, verify production `DATABASE_URL` / `APP_DATABASE_URL` / `SUPABASE_URL` point at the same project you reset in preview, and that `RESEND_API_KEY` / `SENDER_EMAIL` match preview. Remember: pre-existing prod secret values are **not** overwritten by redeploy — if preview's `.env` was edited later, you must update the value in the Secrets tab (and redeploy) for prod to pick it up. If prod turns out to be a *different* DB, that alone explains why your preview reset didn't help, and Fix 1 must be applied against that prod DB.

## Optional hardening (not the cause)
Consider exempting the superadmin account from the `mfa_send` 8/24h limiter, or raising its ceiling — otherwise normal superadmin login testing will keep self-inflicting this 429. This is a product/code decision, not a deployment bug.
