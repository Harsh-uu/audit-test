# RCA — "Invite email failed to send" on Super Admin → Invite Admin (prod)

## Scope
Deployment: transcript-vault-2 (https://1two.one / https://transcript-vault-2.emergent.host)
Active run: 2b5874f0-21a3-4d17-857f-d952512e4fd9
Flow: POST /api/super-admin/orgs/{org_id}/invite → utils/org_provisioning.py::send_invite_email → resend.Emails.send(...)
This is a DIFFERENT code path from the prior MFA rate-limit issue.

## Exact production evidence (not inferred)
Grep of production backend logs (active run, Loki) for "Invite email failed" over the last 24h returned exactly one match, timestamped around the Walfinch Oxfordshire invite:

```
2026-10-12 13:43:27,569 - utils.org_provisioning - WARNING - Invite email failed (user still created): The 1two.one domain is not verified. Please, add and verify your domain on https://resend.com/domains
```

This is the exception text caught by the `except ... as e` / `logger.warning(f"Invite email failed (user still created): {e}")` branch, which then returns False and drives the "User created — email failed to send — share the link manually" UI state.

## Root cause
Resend rejected the send because the message's **from/sender domain `1two.one` is not verified** in this Resend account. The exception is a Resend domain-verification rejection — NOT an auth/invalid-API-key error, NOT a per-recipient domain rejection, NOT a timeout, NOT a quota issue.

## Why the preview test passed but prod failed
The preview test sent to `delivered@resend.dev` (Resend's own test inbox), which Resend accepts on the free/sandbox path irrespective of sender-domain verification. A real production invite uses a `@1two.one` from-address (SENDER_EMAIL), and sending from an unverified custom domain is blocked. So the preview success does not exercise the same constraint. API key validity and quota (daily 6/100, monthly 29/3000) are confirmed irrelevant.

## Fix (owner: User / third-party Resend dashboard)
Two viable paths:
1. Verify the `1two.one` domain on Resend: https://resend.com/domains → add domain → publish the shown SPF/DKIM DNS records at the 1two.one registrar → wait for Resend to mark it verified. After that, re-sending works with no code change.
2. OR, until the domain is verified, set SENDER_EMAIL to a from-address on an already-verified domain (e.g. Resend's onboarding domain) in Deployment Panel → Secrets, then redeploy. This is a stopgap; the long-term fix is path 1 so emails come from 1two.one.

No manifest or source bug is involved. The app behaves correctly — it catches the failure, still creates the user, and surfaces a manual accept-invite link. The only change needed is operational: verify the sender domain in Resend (and/or adjust SENDER_EMAIL).
